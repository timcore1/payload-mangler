# payload-mangler

<img width="1280" height="640" alt="payload-mangler-banner" src="https://github.com/user-attachments/assets/53d317ea-06d2-4b4c-bea7-ad1251006cd0" />


CLI-утилита на Python 3 для мутации security-payload'ов (SQLi / XSS) и проверки
того, как на них реагирует фильтр локального лабораторного стенда: WAF, валидатор,
самописная проверка ввода.

Утилита берёт известные «плохие» строки, прогоняет их через набор детерминированных
мутаторов (URL-кодирование, SQL-комментарии, смена регистра, null-байты…), отправляет
каждый вариант на стенд и классифицирует ответ: заблокировано, отражено в теле,
прошло насквозь или упало с ошибкой БД.

## Как это работает

1. **Проверка периметра.** `check_scope(url)` вызывается до любого сетевого запроса.
   Если цель не loopback — сообщение в `stderr` и код возврата `2`.
2. **Чтение payload'ов** из файла (по одному в строке; пустые строки и строки,
   начинающиеся с `#`, пропускаются) или из `--payload`.
3. **Генерация мутантов.** Каждый payload × каждый выбранный мутатор; с `--chain`
   добавляются все упорядоченные пары мутаторов. Одинаковые получившиеся строки
   отправляются один раз (порядок сохраняется).
4. **Baseline-запрос** с пустым payload'ом — чтобы отличить «страницу приложения»
   от реакции на payload, затем пакетная отправка (`ThreadPoolExecutor`).
5. **Классификация.** Каждый ответ → вердикт (по фильтру) + проверка oracle-регэкспа
   + флаг `reached_backend` (признак, что запрос дошёл до БД).
6. **Вывод.** Таблица в консоль, при `--report` — JSON, в конце одна строка итога.

## Требования и установка

- Python **3.11+** (используется `enum.StrEnum`), проверено на 3.12.7 / Linux ARM64
- `requests` (единственная внешняя зависимость, остальное — stdlib)

```bash
git clone <repo-url> payload-mangler
cd payload-mangler

python3 -m venv .venv && source .venv/bin/activate
pip install requests

# проверка, что всё на месте
python3 -m payload_mangler --help
```

Пакет не требует установки: `python3 -m payload_mangler` запускается **из корня
проекта** (там, где лежат каталоги `payload_mangler/` и `payloads/`).

## Быстрый старт

```bash
python3 -m payload_mangler \
  --url 'http://127.0.0.1:3000/rest/products/search?q={{PAYLOAD}}' \
  --payload-file payloads/sqli.txt \
  --mutations all --chain \
  --oracle-regex '"data":\[\{' \
  --report out.json
```

- `{{PAYLOAD}}` — маркер, на место которого подставляется мутированная строка
  (в URL или в `--data`; подстановка идёт **как есть**, без дополнительного
  кодирования — payload уже мутирован).
- `--oracle-regex` — маркер успеха, который ищется в теле ответа. Если не задан,
  oracle считается сработавшим всегда.
- `--report out.json` — сохранить все находки для последующего разбора.

POST-вариант:

```bash
python3 -m payload_mangler \
  --url 'http://127.0.0.1:3000/rest/user/login' \
  --method POST --data 'email={{PAYLOAD}}&password=x' \
  --payload "' OR 1=1--" \
  -H 'Content-Type: application/x-www-form-urlencoded' \
  --cookie 'session=abc123'
```

Одиночный мутатор для быстрой проверки:

```bash
python3 -m payload_mangler \
  --url 'http://127.0.0.1:3000/rest/products/search?q={{PAYLOAD}}' \
  --payload-file payloads/xss.txt \
  --mutations unicode_escape --oracle-regex 'alert\(1\)'
```

## Пример вывода

Реальный прогон против локального стенда (5 payload'ов из `payloads/sqli.txt`,
мутаторы `url_encode` и `double_url_encode`, флаг `--no-color`):

```
[1/10] 500 52b 1.4ms '%27%20OR%201%3D1--'
[2/10] 200 51b 0.9ms '%2527%2520OR%25201%253D1--'
... (по строке прогресса на каждый запрос)

 № CHAIN             VERDICT     ORACLE BACKEND STATUS SIZE  MS
-- ----------------- ----------- ------ ------- ------ ---- ---
 1 url_encode        REFLECTED   no     yes        500   52 1.4
 2 double_url_encode PASSTHROUGH yes    no         200   51 0.9
 3 url_encode        REFLECTED   no     yes        500   62 1.0
 4 double_url_encode PASSTHROUGH yes    no         200   51 1.4
 5 url_encode        REFLECTED   no     yes        500   77 1.6
 6 double_url_encode PASSTHROUGH yes    no         200   51 0.7
 7 url_encode        BLOCKED     no     no         403   24 0.8
 8 double_url_encode BLOCKED     no     no         403   24 0.9
 9 url_encode        REFLECTED   no     yes        500   60 1.0
10 double_url_encode PASSTHROUGH yes    no         200   51 0.7
10 mutants: 2 blocked, 4 passthrough+oracle, 4 reached_backend, 0 error
```

Как это читать:

- строка **7–8**: `' UNION SELECT NULL--` → `403` → **BLOCKED** (красный) — фильтр
  сработал;
- строка **1**: ответ `500` с `SQLITE_ERROR` в теле → **REFLECTED** + `BACKEND=yes` —
  фильтр пропустил, запрос дошёл до базы и она отвалилась с синтаксической ошибкой.
  Именно это и есть признак успешного обхода;
- строка **2**: `PASSTHROUGH` + `ORACLE=yes` (зелёный) — ответ чистый, payload не
  отражён, но маркер успеха из `--oracle-regex` в теле есть;
- итог: `10 mutants: 2 blocked, 4 passthrough+oracle, 4 reached_backend, 0 error`.

`STATUS=ERR` печатается, когда ответа не было вовсе (сетевая ошибка).

## Флаги

| Флаг | Описание |
|---|---|
| `--url URL` | **обязателен**, целевой URL; должен содержать `{{PAYLOAD}}` (или маркер в `--data`) |
| `--method {GET,POST}` | HTTP-метод, по умолчанию `GET` |
| `--data BODY` | тело запроса (POST), может содержать `{{PAYLOAD}}` |
| `-H, --header 'Key: Value'` | дополнительный заголовок, **повторяемый** |
| `--cookie 'k=v; k2=v2'` | cookies одной строкой |
| `--payload-file PATH` | файл с payload'ами (по одному в строке, `#` — комментарий) |
| `--payload PAYLOAD` | один payload (взаимоисключающе с `--payload-file`) |
| `--mutations LIST` | список имён через запятую или `all` (по умолчанию `all`) |
| `--chain` | добавить все **упорядоченные пары** мутаторов (через `apply_chain`) |
| `--oracle-regex REGEX` | регэксп-маркер успеха в теле ответа (по умолчанию срабатывает всегда) |
| `--proxy URL` | прокси, например `http://127.0.0.1:8080` |
| `--delay SECONDS` | пауза между запросами **на поток**, по умолчанию `0.1` |
| `--threads N` | потоков, `1..16`, по умолчанию `4` |
| `--report PATH` | записать находки в JSON |
| `--no-color` | отключить ANSI-раскраску таблицы |

Коды возврата: `0` — успех, `2` — ошибка использования или цель вне периметра,
`130` — прерывание по `Ctrl+C`.

## Мутаторы

10 чистых функций `str -> str`; `--mutations all` включает все, `--chain` — ещё и
все пары в обоих порядках (порядок важен, мутаторы не коммутируют).

| Имя | Что делает | Пример |
|---|---|---|
| `url_encode` | однократное URL-кодирование спецсимволов | `' OR 1=1--` → `%27%20OR%201%3D1--` |
| `double_url_encode` | двойное кодирование (`%` → `%25`) | `'` → `%2527` |
| `case_swap` | случайная смена регистра букв (seed=42, детерминированно) | `UNION` → `UnioN` |
| `comment_inject` | разрыв SQL-ключевых слов комментарием | `UNION SELECT` → `UN/**/ION SE/**/LECT` |
| `whitespace_swap` | пробелы → `%09` / `%0a` / `%0c` / `/**/` | `1 OR 1` → `1%09OR%091` |
| `null_byte` | `%00` перед кавычками и скобками | `')` → `%00'%00)` |
| `unicode_escape` | ASCII-буквы → `\u0065` (XSS-контекст) | `ab` → `\u0061\u0062` |
| `hex_encode` | строковые литералы в кавычках → `0x...` | `'admin'` → `0x61646d696e` |
| `concat_split` | `'admin'` → `'adm'\|\|'in'` (SQLite) | `'admin'` → `'adm'\|\|'in'` |
| `newline_bypass` | `\n` после `--` | `1=1--` → `1=1--\n` |

## Вердикты и колонка BACKEND

Вердикт описывает **реакцию фильтра**, а не успех атаки:

| Вердикт | Значение |
|---|---|
| `BLOCKED` | фильтр отказал: статус `403`/`406` или в теле сигнатура блокировки (`Unexpected path`, `Request blocked`, `ModSecurity`, …) |
| `REFLECTED` | payload (в исходном или URL-декодированном виде) вернулся в теле ответа |
| `PASSTHROUGH` | чистый ответ без нашего payload'а |
| `ERROR` | ответа не было: сетевая ошибка, таймаут |

Отдельная колонка `BACKEND` отвечает на другой вопрос — **дошёл ли payload до базы**:
`yes`, если в теле найдена сигнатура ошибки БД (`SQLITE_ERROR`, `SQL syntax`,
`sqlite3.OperationalError`, `mysql_fetch`, `ORA-0`).

Комбинация, ради которой всё делалось:

```
PASSTHROUGH  ORACLE=yes  BACKEND=yes   ← фильтр обойдён, запрос дошёл до БД
BLOCKED      ORACLE=no   BACKEND=no    ← фильтр сработал
```

Сигнатуры, которые уже присутствуют на baseline-странице (пустой payload), блокировкой
не считаются — это защита от ложных срабатываний на «Forbidden» в подвале сайта.

## JSON-отчёт

`--report out.json` пишет список находок с отступами (каталоги создаются на лету):

```json
[
  {
    "original_payload": "' OR 1=1--",
    "mutated_payload": "%27%20OR%201%3D1--",
    "chain": ["url_encode"],
    "verdict": "reflected",
    "status_code": 500,
    "size": 52,
    "elapsed_ms": 1.4,
    "oracle_true": false,
    "backend": true
  }
]
```

Поля: `original_payload` (что было в файле), `mutated_payload` (что реально ушло),
`chain` (применённые мутаторы по порядку), `verdict` (`blocked` / `reflected` /
`passthrough` / `error`), `status_code` (`null`, если ответа не было), `size`,
`elapsed_ms`, `oracle_true`, `backend`.

## Защита от выхода за периметр

Разрешены только loopback-цели:

```python
ALLOWED = {"127.0.0.1", "::1", "localhost"}
```

Проверяется и литеральный хост, и результат DNS-резолва. Всё остальное — публичные
IP, адреса локальной сети (`192.168.x.x`), домены, а также имена, которые **не
резолвятся**, — отклоняется с кодом возврата `2`:

```
$ python3 -m payload_mangler --url 'http://8.8.8.8/?q={{PAYLOAD}}' --payload 1
scope error: out of scope: '8.8.8.8' (resolved to 8.8.8.8); allowed targets: 127.0.0.1, ::1, localhost
$ echo $?
2
```

**Обходного флага (`--allow-remote`, `--i-know-what-im-doing` и подобных) нет и не
планируется** — это осознанное ограничение, а не недоделка. Проверка выполняется до
создания HTTP-сессии, поэтому «случайно» отправить запрос на чужой хост нельзя.

## Структура проекта

```
payload-mangler/
├── payload_mangler/
│   ├── __init__.py      # публичный API пакета
│   ├── __main__.py      # CLI: argparse, оркестрация, сводка
│   ├── mutations.py     # 10 мутаторов + MUTATIONS + apply_chain
│   ├── engine.py        # build_request / send / run_batch (HTTP, потоки, ретраи)
│   ├── detector.py      # Verdict, classify, reached_backend, baseline
│   ├── oracle.py        # make_oracle(pattern) -> check(response)
│   ├── report.py        # Finding, print_table, save_json
│   └── scope.py         # ALLOWED, ScopeError, check_scope
├── payloads/
│   ├── sqli.txt         # 5 стартовых SQLi-payload'ов
│   └── xss.txt          # 3 стартовых XSS-payload'а
├── tests/
│   ├── test_mutations.py
│   ├── test_engine.py
│   ├── test_detector.py
│   ├── test_oracle.py
│   ├── test_report.py
│   ├── test_scope.py
│   └── test_cli.py
├── pytest.ini
└── README.md
```

Модули разделены по ответственности: `mutations` — чистые преобразования строк,
`engine` — единственное место, где есть сеть, `detector`/`oracle` — интерпретация
ответа, `report` — вывод, `scope` — предохранитель, `__main__` — склейка.

## Ограничения

- Только `GET` и `POST`; multipart, JSON-тела и загрузка файлов не поддерживаются.
- `--chain` строит **упорядоченные пары** мутаторов, а не произвольные цепочки
  длиной 3+. Дубликаты мутированных строк отбрасываются, поэтому фактическое число
  запросов может быть меньше теоретического (`5 payload'ов × 100 цепочек → 199`
  запросов в примере выше).
- Oracle — это регулярное выражение по телу ответа; сравнение baseline-размеров,
  таймингов и слепые техники (boolean/time-based) не реализованы.
- `BACKEND`-сигнатуры зашиты в `detector.BACKEND_SIGNALS` (SQLite, MySQL, Oracle);
  для других СУБД список нужно расширять.
- Раскраска: `--no-color` либо переменная окружения `NO_COLOR`.
- IPv4/IPv6: резолв выполняется через `socket.gethostbyname` (IPv4); `::1`
  распознаётся по литералу.
